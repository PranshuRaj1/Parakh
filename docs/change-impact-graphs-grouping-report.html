Change Impact Graphs and Behavior Grouping

What German, Hassan, and Robles propose, what it means for the current review planner, and the smallest changes likely to make grouping more accurate and more useful.

Executive finding: The paper supports the direction of graph-based grouping, but it points to a more precise design. Group changes around dependency-mediated behavior, keep historical change evidence separate from ordinary context, and rank or filter the graph instead of treating every connected node as equally important.

2. What the paper says

Software failures often appear in code that was not recently edited. A previous change can affect that code through calls, data dependencies, or other relationships. Starting at the failure location and manually walking the dependency graph is slow. Traditional program slicing can also return a very large set of possible locations.

The paper proposes Change Impact Graphs, or CIGs. The method first recovers which functions changed in the past from version-control history. It then propagates the effect of those changed functions through a dependence graph. The result is a graph in which recent historical changes are marked, allowing a maintainer to focus on a smaller, more relevant part of the system.

The important distinction is that the graph is not merely a map of files changed in one commit. It is a map of changed behavior and its possible impact, including unchanged code through which the impact travels.

3. Main ideas to carry into our planner

1Impact is propagated

Dependencies should explain why two changes belong to the same behavior, even when the connecting code itself was not edited.

2History is evidence

Commit age, changed functions, and prior changes help prioritize impact. They should not be confused with the static dependency graph.

3Graphs need filtering

The goal is to reduce investigation effort, not to display every reachable node. Relevance and compactness are first-class requirements.

How this differs from a file grouping strategy

A file strategy assumes that all changes in one file should be reviewed together and that changes in different files are separate. CIG-style grouping instead asks whether the changes participate in the same behavior through dependency paths. This is closer to the question a reviewer needs to answer: “What behavior could these changes jointly alter?”

4. Current implementation diagnosis

The current implementation already has a useful foundation: semantic changes, indexed symbols, typed edges, graph components, confidence levels, context rendering, and file fallback. The main issue is where the dependency information enters the pipeline.

The local evaluation notes report a 73.9% fallback-unit rate and higher average input tokens for grouped review than file review. That pattern is consistent with a planner that adds context but does not yet obtain enough reliable cross-file grouping value. It is a routing and graph-construction problem, not proof that behavior grouping is the wrong objective.

5. Recommended grouping design

Phase 1: Add unchanged bridge traversal

Build a bounded impact view around changed symbols. Traverse one or two unchanged nodes through strong typed edges. If changed A and changed B are connected by a short, strong path, add a group edge between A and B and record the bridge path as evidence.

changed A -> unchanged service -> unchanged repository -> changed B
             group edge: A <-> B
             evidence: calls, hop distance 2, bridge symbols [service, repository]

Do not make bridge nodes review members. They should be context with direction, edge type, hop count, and the changed anchors they connect.

Phase 2: Replace binary connectivity with weighted evidence

Connected components are a good baseline, but one weak edge can create a large and noisy component. Start with explicit weights and require either one strong relation or multiple independent signals.

EvidenceStarting weightUse
Direct call, implementation, or override relation5Strong join
One-hop unchanged bridge4Strong join with path evidence
Type, schema, route, export, or configuration-key relation3Join when direction and identity are reliable
Same changed file2Supporting signal only
Matching identifier basename1Never sufficient alone

Phase 3: Split by graph locality

When a group exceeds the context budget, choose the highest-risk or highest-degree changed anchor, expand through the strongest edges, and stop at the character limit. Start the next group from the highest-ranked unassigned change. This preserves behavior neighborhoods instead of slicing by sorted IDs.

Phase 4: Demote only ambiguous changes

Keep reliable portions of a component grouped. Send only low-confidence changes, or small neighborhoods whose evidence does not pass the join threshold, to file fallback. Track the reason per change so the dashboard can distinguish parser weakness from genuinely weak relatedness.

Phase 5: Treat context as required, supporting, or optional

6. Suggested data model changes

The smallest useful extension is to preserve bridge evidence and edge confidence without changing the public review-unit shape too much.

interface ImpactEvidence {
  fromChangeId: string;
  toChangeId: string;
  path: Array<{ symbol: string; edgeType: string }>;
  score: number;
  reasons: string[];
}

interface BehaviorGroup {
  // existing fields
  impactEvidence?: ImpactEvidence[];
  requiredContext?: string[];
  supportingContext?: string[];
}

Keep group membership limited to changed items. This avoids sending every bridge symbol to the reviewer while preserving enough provenance to explain the grouping and debug false joins.

7. Evaluation plan

Run the same corpus, model, judge, and token budget through three planners:

  1. A: current direct changed-node graph.
  2. B: current graph plus bounded unchanged bridge traversal.
  3. C: weighted bridge graph, graph-local splitting, and local demotion.

Do not use final defect F1 as the only measurement. Add:

MetricQuestion answered
Group recall and precisionDid the planner put behaviorally related changes together without noisy joins?
Related-file retrieval recallDid the selected group context contain files needed to understand the change?
Fallback rateHow often did the planner lack enough evidence to use a behavior group?
Required-context retentionDid token trimming preserve direct dependencies?
Input tokens and review callsDid grouping reduce cost rather than add context overhead?
Defect recall and F1Did the end-to-end review outcome improve?
Acceptance bar: bridge grouping should increase related-file and group recall, materially reduce fallback, and lower or maintain input tokens. End-to-end defect recall must not regress against the file baseline. Judge-unstable cases should be reported separately.

8. Bottom line

The paper’s most useful lesson for this project is simple: a change group should represent an impact neighborhood, not merely a set of changed files or directly changed symbols. The first implementation step should therefore be unchanged bridge traversal with explicit path evidence. After that, weighted joins, graph-local splitting, and local demotion should make the grouping both more accurate and less conservative.

Embeddings or broad semantic retrieval should come later. The current bottleneck is deterministic graph structure and trustworthy measurement. Fixing those first gives the team a clear signal about whether more advanced retrieval is needed.
