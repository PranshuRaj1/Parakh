Iteration timeline

Iteration 1: establish semantic grouping foundations 2026-09-03

fdd3849, 076b6e8, 0809410, 6c4b823, cfa4e1c

Changes. Added changed-symbol indexing across benchmark languages; connected behavior groups with corroborated code relationships; loaded bounded dependency context; rendered grounded multi-file review units; and ran semantic grouping in production shadow mode.

Why. File-by-file review repeats context and cannot express that several changed files implement one behavior. The intended architecture was to parse changed entities, build a repository graph, form behavior groups, and ask Gemini to review a coherent multi-file unit.

Assumptions. Symbol extraction would be reliable enough to anchor changed hunks. Indexed calls, imports, exports, and related facts would provide useful grouping evidence. Grouped prompts would improve context reuse without degrading localization.

Risk accepted. Unsupported or ambiguous changes could fall back to file review. This made the first version safer, but also created the possibility that the fallback would dominate the experiment.

Iteration 2: make file fallback bounded and safer 2026-09-04

9645b25, 7f8e059

Changes. Bounded semantic review with file fallback and avoided cross-suite duplicate test findings.

Why. A grouping system must not force low-confidence symbol matches into a multi-file prompt. Fallback provides a correctness escape hatch, while duplicate-test suppression prevents the new context path from creating repeated findings.

What this made visible. The fallback was not just a safety net. It became a major routing decision, so fallback rate had to be measured explicitly instead of looking only at final F1.

Iteration 3: add the latest-eval and dashboard workflow 2026-09-04

1eb9d77, b763e48, 2da3eb3, d24eace, db3e1bf, 8fe21a2, 7e626cc

Changes. Added a visual eval dashboard, remembered the latest comparison, added a latest-eval runner, reused eval configuration, aligned cache identity with config checks, fixed Windows launching, and streamed process output.

Why. Re-running long evaluations without stable identity and visible progress made it difficult to know whether a result was new, cached, stuck, or using different settings.

Observed issue. The CLI could remain silent while Gemini calls were still running. Report files were written before later publication steps, so seeing Markdown and JSON reports did not necessarily mean the whole command had finished.

Iteration 4: stabilize adjudication and cache behavior 2026-09-03 to 2026-09-06

0050d3c, 026a913, 4afb97a, c849eaf, 3f11c94

Changes. Versioned eval strategy and planner cache identity; normalized judge disagreement and quota recovery; preserved generic rate-limit errors; rotated Groq judge keys across accounts; and resumed partial judge cache entries safely.

Why. A comparison is only meaningful if cache keys include the corpus, pipeline, configuration, and strategy. Judge retries and partial entries also needed to avoid replaying or silently accepting incomplete adjudication.

Important distinction. Gemini reviewer calls and Groq judge calls have separate cache behavior. A rerun can reuse cached work when the identity matches, but a changed corpus, pipeline SHA, configuration, or strategy should invalidate the relevant result.

Iteration 5: expand retrieval context and improve measurement 2026-09-06

a6efd62, f735998, 1c52ea5, cb3ecb5

Changes. Improved semantic dependency context; added retrieval tracking and eval history; added expanded corpus fixtures; and updated provider logging and rollout behavior.

Why. The original corpus did not populate expectedRelatedFiles, so retrieval recall could not be measured. The expanded context corpus introduced unchanged files and a ground-truth field to separate “the graph did not retrieve the right file” from “Gemini reviewed the context poorly.”

Ground-truth policy. Each case received two to five files judged necessary to understand the changed behavior. Generic logging, broad utilities, and test framework files were not labeled unless the defect depended on them.

Iteration 6: bridge traversal and grouped pipeline commit 2026-09-06

b15982c: Improve eval behavior grouping

Changes. Added bounded traversal through unchanged bridge symbols, graph context tracking, group-building behavior, local component splitting and demotion tests, and eval-side grouping metrics.

Why. The graph previously stored unchanged dependencies as decorative context. A path such as changed controller -> unchanged service -> changed repository could not connect two changed symbols during grouping. Bridge traversal made the unchanged symbol participate in the connection while retaining only changed symbols as group members.

Safety decisions. Traversal used strong typed relations, a two-hop limit, per-component and total path caps, and a per-bridge-symbol fan-in cap. Components were split before confidence demotion, so demotion percentages were calculated on the final sub-component rather than stale pre-split composition.

Iteration 7: context corpus repair and annotation 2026-09-07

Working tree, not committed

Failure. A direct patch to the large generated context JSON corrupted its escaping. Attempts to repair invalid escapes with a scanner made the situation worse by confusing valid escaped backslashes and quotes with malformed sequences.

Diagnosis. The original selected corpus still parsed. The expanded file failed JSON parsing only after the large artifact was edited. Regenerating the expanded file restored valid JSON.

Fix. Stopped repairing the artifact in place; regenerated it from the original corpus; changed the annotation helper to parse only valid JSON and to locate the JSON argument robustly; applied labels; and verified all 15 cases, 39 labels, and zero missing paths.

Lesson. Generated artifacts should be regenerated by their producer rather than patched directly, especially when they contain source code with many escape sequences.

Iteration 8: latest eval with retrieval ground truth 2026-09-07

Observed against b15982c

Result. The new report used martian-selected-context-v1 and showed that retrieval labels were active. Related-file retrieval recall averaged 47.8%. The grouped pipeline was assessed as better in three cases, parity in ten, pass in one, and judge-unstable in one, with no worse cases.

Iteration 9: fix over-broad fallback filtering 2026-09-07

Working tree, not committed

Root cause. groupedReviewUnits collected demoted files and removed every change in those files from behavior groups. A single low-confidence change therefore discarded reliable changes sharing its file.

Fix. The behavior-group filter now tracks exact demoted change IDs. Low-confidence changes still receive file fallback, but reliable changes in the same file remain eligible for behavior-group review.

Verification. The targeted grouping and branch-pipeline suites passed: 23 tests passed across two test files. The full eval has not yet been rerun against this uncommitted fix, so the improvement is not yet measured.

How the current system works

changed diff
  -> semantic changes and confidence
  -> base/head repository indexes
  -> changed-symbol graph
  -> strong components and bounded bridge traversal
  -> component splitting
  -> local confidence demotion
  -> behavior review units plus file fallbacks
  -> Gemini reviewer calls
  -> Groq judge adjudication
  -> metrics, comparison report, dashboard, publication

Important data-model boundary

Changed symbols are graph nodes. Unchanged dependency symbols are context nodes and bridge evidence. The bridge node helps form an edge between changed symbols, but it is not itself reviewed as a changed member.

Important routing boundary

A behavior unit is eligible for a multi-file review call. A fallback unit uses the ordinary file-review adapter. The current eval reports both the final review quality and the routing statistics, because a good F1 score can hide a system that is doing almost no grouping.

Explicit assumptions made during the work

  • The original selected corpus is the stable baseline and should not be rewritten.
  • Expanded context labels are ground truth for necessary files, not a claim that every retrieved file is useful.
  • Unchanged bridge nodes should connect changed symbols but should not become review findings themselves.
  • Strong typed relations are safer grouping evidence than basename similarity or generic logging relationships.
  • When a change cannot be mapped reliably to a symbol, file fallback is safer than speculative grouping.
  • Judge-unstable cases are diagnostic evidence and should not be counted as definitive grouping wins or losses.
  • The current 15-case corpus is too small to treat single-digit percentage-point changes as conclusive.

Iteration 9: quality improvement plan

Planned 2026-09-07. No implementation from this plan has been applied yet. The logging change is committed in 307dbe2; the quality work below starts from that verified baseline.

Decision. The next work must be staged in dependency order: first repair fallback routing, then inspect and repair symbol and graph coverage, then reduce fragmentation, then isolate test review, and finally change score interpretation for judge instability. Scoring weights will not be changed before retrieval and graph evidence explain the zero-recall cases.

Implementation sequence

  1. Verify the committed baseline. Run the targeted grouping, branch-pipeline, adjudication, metrics, and orchestrator tests. Re-run the expanded corpus only with cache identity visible. Record the current per-case group count, fallback changes, file calls, behavior calls, rendered related files, input tokens, F1, and judge status before each code change.
  2. Make fallback hunk-scoped. Introduce one deterministic renderer that accepts a set of change IDs or patch hashes and emits only the corresponding unified hunks. In the grouped adapter, pass demoted change evidence to the file fallback unit. Preserve unchanged source context only when it is needed for those demoted hunks, and cap it independently. Do not use the full file diff when the file also has reliable grouped changes.
  3. Keep fallback ownership exact. Track primary evidence ownership by change ID and patch hash. Assert that each change is reviewed exactly once, either in one reliable behavior unit or in one fallback unit. A file may have multiple fallback hunks, but those hunks must not re-enter a behavior unit or an all-file fallback unit. Preserve a separate file-level fallback only for files with no planner-owned change evidence.
  4. Inspect zero recall before changing weights. Add a diagnostic snapshot for each expected file with: source present or absent, extracted symbols, changed-line to symbol mappings, indexed imports, indexed edges, graph edges, bridge paths, context nodes, rendered context markers, and truncation status. Run it for the Sentry uptime case and the Grafana SQL case. For the Sentry case, specifically inspect Python module imports, model/type references, configuration declarations, and test-to-production links. For Grafana, inspect Go package imports, receiver methods, type references, and test file relationships.
  5. Repair the smallest missing extraction seam. Prefer improving parser adapters and edge construction over score changes. Add explicit symbol kinds or relationship records for configuration and framework registration only where the fixture demonstrates a real missing relationship. Improve path resolution for the languages involved, preserve import aliases and package identity, and add tests that assert the exact expected edge or bridge path. Do not add broad same-directory edges as a substitute for semantic evidence.
  6. Reduce fragmentation with evidence-preserving connection rules. After extraction is correct, connect related changed nodes through verified calls, imports, type references, configuration keys, registration identifiers, and direct test coverage. Use bounded multi-hop traversal with deterministic ordering. Measure component purity and completeness before and after. If a component exceeds size limits, split by weakest cut or stable seeded expansion while keeping production behavior changes together and retaining explicit lineage.
  7. Separate production and test review. Classify files using the existing test path convention plus language-specific test conventions. Build production groups first. Attach test changes as a separate test-review group when they contain meaningful changed evidence. Permit an explicit production-to-test link in metadata for coverage context, but do not let test-only edges merge the primary production group. Give test groups their own calls, findings, and metrics so test sleeps or exception handling cannot dominate production scoring.
  8. Exclude unstable cases from the primary score. Keep every unstable case in the report for diagnosis, but compute the headline comparison over cases whose old and new adjudications are stable. Report both the stable-only score and the all-case descriptive score, with the unstable case count and held-out rate. Do not silently convert disagreement into a pass, failure, or parity result. Require the judge to produce consistent verdicts in a repeat run before returning a case to the primary score.
  9. Run one-variable evaluations. First measure hunk-scoped fallback alone. Then measure extraction and edge fixes. Then measure grouping and production/test separation. Finally measure judge-score exclusion. Each run must use a distinct strategy or working-tree identity, retain the same corpus and reviewer configuration, and compare against the same baseline.

Why this order matters

Fallback duplication is a direct routing bug with a clear token-level oracle, so it should be fixed before interpreting cost or call-count changes. Zero recall is a graph-input problem until proven otherwise. If the expected file never becomes a symbol, edge, context node, or rendered context marker, changing weights only changes the ranking of evidence that does not exist. Fragmentation should be addressed after graph coverage because merging weakly connected nodes can hide unrelated changes. Test separation should be measured after production connections are known, otherwise it is impossible to tell whether a new boundary fixed a real graph edge or only removed useful context. Judge instability belongs last in the scoring layer because it changes interpretation, not review planning.

Acceptance gates

  • Mixed files show no duplicate reliable hunk in fallback prompts.
  • All planner changes have exactly one execution owner.
  • Sentry uptime and Grafana target cases have nonzero retrieval recall, with the exact extraction or edge path recorded.
  • Uptime group count and provider calls decrease without a production defect-recall regression.
  • Test-only findings are reported in test units and do not determine the production group assessment.
  • Three judge-unstable cases remain visible but are excluded from the primary score until repeated verdicts stabilize.
  • Targeted tests, full relevant eval tests, and a fresh expanded-corpus run pass with cache identity and token metrics recorded.

Open questions to resolve during implementation

  • Whether Sentry's expected model and uptime files are absent because Python declarations are not extracted, because imports are unresolved, or because the files are present but context rendering truncates them.
  • Whether Grafana's expected test relationship is direct package or type coupling, or whether it should remain a separate test group with only coverage metadata.
  • Whether 13 uptime provider calls are caused mainly by missing graph edges, the 2-hop bridge limit, the renderer character cap, or the current group partition strategy.
  • Whether unstable judge cases are caused by insufficient judge context, genuinely ambiguous findings, or reviewer output variance. The score policy should not hide this distinction.

Planned outcome. The grouped pipeline should review each changed behavior once, use fallback only for the evidence that needs it, retrieve expected related files through explainable graph paths, keep production behavior coherent, isolate test quality, and report stable score changes without allowing judge variance to masquerade as grouping quality.

Iteration 10: stable-case eval confirms improvement, but routing remains broken

Evidence received 2026-09-07. Compared old file-strategy with new grouped-strategy. Judge-unstable cases were excluded from the primary comparison.

What is improving. On stable cases, strict F1 increased from 0.298 to 0.470, precision increased from 0.417 to 0.542, and recall increased from 0.213 to 0.380. This is a real positive signal that grouped review finds more ground-truth defects when its routing and context are effective.

Why this changes the interpretation. The older 15-case result in this history showed only a small F1 movement from 20.8% to 22.4%, with the new approach assessed as worse. The newer stable-case result contradicts that older conclusion because the grouping pipeline has improved since then. The correct conclusion is not that grouping failed. It is that grouping has become useful but is not yet reliable across repositories and change shapes.

Judge stability confirmation

Three of fifteen cases, or 20%, were judge_unstable. This validates the plan's decision to exclude unstable cases from the primary score. The stable-case improvement is the correct headline signal for now, while the all-case result remains useful only as descriptive diagnostic evidence.

Updated conclusion

The grouping approach is producing a meaningful quality improvement when it works: stable-case F1, precision, and recall all increased. However, the improvement is uneven because review planning still has three unresolved weaknesses: fallback remains the dominant route and can repeat reliable content, graph coverage misses required related files, and fragmented groups increase context and provider work without consistently improving precision. The reported results support the existing implementation order: fallback deduplication first, retrieval diagnostics and parser or edge repair second, fragmentation reduction third, test separation fourth, and stable scoring policy fifth.

Next measurement requirements

  • Report fallback input tokens separately from behavior-group input tokens.
  • Report repeated patch hashes and files across review units.
  • Report expected-file retrieval, rendered-file retrieval, and finding evidence grounding as separate metrics.
  • Report group count, provider calls, context size, and test versus production group counts for Sentry uptime.
  • Report exact missing graph edges for Grafana and Keycloak before any score-weight changes.
  • Keep the stable-only score as the primary comparison while exposing the three unstable cases separately.

Iteration 11: implementation approved and started

Approved 2026-09-07. Implementation begins from committed progress logging change 307dbe2 with the HTML plan updates retained as working documentation.

Execution decision. Implement the plan in isolated phases. The first phase is hunk-scoped fallback because it has the clearest defect boundary and the strongest cost oracle. Retrieval and graph changes will not be layered on top until fallback ownership is test-verified.

Phase order

  1. Verify the baseline tests and clean code baseline.
  2. Render fallback review units from demoted evidence only.
  3. Add exact change ownership and mixed-file regression tests.
  4. Run the expanded eval and record per-unit token and duplication metrics.
  5. Diagnose Sentry, Grafana, and Keycloak extraction and graph paths.
  6. Repair the smallest parser or edge seams found by the diagnostics.
  7. Reduce fragmentation, separate test review, and stabilize score interpretation.

Phase 1 result: hunk-scoped fallback

Implementation. worker/src/review/eval/branch-pipeline.test-helper.ts now identifies fallback evidence by patch hash and renders only the selected semantic hunks. If one hunk contains both reliable and demoted symbol mappings, the entire hunk is assigned to fallback so it cannot be reviewed twice. Full-file fallback remains available only for files that have no planner-owned changes.

Why. Change-level filtering alone can still duplicate a hunk when multiple semantic changes share the same patch hash. Hunk-level ownership makes the execution boundary exact and prevents reliable grouped content from re-entering fallback.

Verification. Added expectations for hunk-scoped fallback and a mixed reliable-plus-demoted same-file regression case. The focused branch-pipeline suite passes:

12 tests passed

Next phase. Add retrieval diagnostics for Sentry uptime, Grafana database performance, and Keycloak group access before modifying graph connectivity or scoring.

Phase 2 result: retrieval diagnostics
