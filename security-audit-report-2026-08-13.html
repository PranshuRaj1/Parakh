Implementation-focused security audit

Authentication exists. Authorization does not.

Parakh correctly verifies GitHub webhooks and uses parameterized database queries, but its trust model collapses at the dashboard and comment boundaries. Any GitHub account can reach repository-scoped data and actions, while untrusted PR commenters can persist review rules that change future bot behavior.

Audit date: 2026-08-13 Target: current working tree Worker + dashboard + DB + history Static review + tests + build + npm advisories

Executive summary

The application is not ready for a public multi-user dashboard or for unrestricted use on public repositories. The top three issues allow cross-repository access, persistent review-policy poisoning, and potential reuse of credentials captured in local git checkpoint history.

Detailed findings

Severity reflects realistic impact in this architecture, not only package advisory labels. Line references describe the audited working tree.

High

PAR-001: Dashboard has authentication but no repository authorization

CVSS-like: 8.8

GitHub sign-in proves identity, but every protected page and API treats any valid session as authority over every repository in the database. Repository names come directly from query parameters or route parameters, and review IDs come directly from URLs. No code checks GitHub membership, collaborator permission, App installation ownership, or a local access-control table.

An attacker needs only a GitHub account and a guessed repository name or review UUID. They can read rules, review findings, model reasoning, stage logs, and raw failure details. They can also create active rules for arbitrary repositories and retry arbitrary failed reviews through the dashboard's shared worker credential.

Required fix

  1. Export one shared NextAuth configuration and persist the GitHub access token or installation identity in the encrypted session.
  2. Add a server-only requireRepoPermission guard to every page, read query, and mutation route. Require at least read access for data and maintain or admin access for rule writes and retries.
  3. Never query by review ID alone. Resolve reviewId together with an authorized repository boundary.
  4. Add integration tests using two users and two private repositories to prove tenant isolation.

High

PAR-002: Untrusted PR commenters can persist active or suppressive rules

Integrity + cost

The webhook validates that GitHub sent the event, but it does not validate that the comment author is trusted to change repository policy. The only identity check excludes the bot itself. In the default mention-only mode, any commenter who can write @parakh can trigger an LLM call. If the classifier labels the text as a correction, the text becomes an immediately active rule. Suppression phrases become instruction rules that deterministically remove matching future findings.

On a public repository this can let an external user weaken security reviews, create contradictory rules, trigger repeated model work, or exhaust provider quotas. The rule is committed before contradiction processing, and contradiction enqueueing fails open.

Required fix

  1. Capture author_association and verify current GitHub repository permission before any review trigger or rule mutation.
  2. Require maintain or admin permission for rule creation and suppression. Consider a two-step approval for suppressive rules.
  3. Use explicit commands for state changes. Do not let free-form intent classification authorize a write.
  4. Add per-user and per-repository rate limits and audit every rule change with actor ID, source comment, and approval state.

High

PAR-003: Credential-bearing environment file exists in local git checkpoint history

Potential full compromise

A high-confidence secret scan found worker/.env.moved in five local checkpoint commits dated 2026-08-09 and 2026-08-10. The historical file contains credential-bearing configuration for the GitHub App, database, Redis, worker API, webhook verification, and LLM providers. Values are intentionally omitted from this report.

The affected commits are reachable only through local refs/t3/checkpoints/... refs in this clone. They are not reachable through the current local remote-tracking branches. That reduces proven exposure, but does not establish that the objects were never synchronized, backed up, copied, or shared. The current .dev.vars, .env.moved, and dashboard environment file are ignored by git.

Required fix

  1. Rotate every credential represented in the historical file, starting with the GitHub App private key, database credential, Redis token, worker API secret, webhook secret, and provider keys.
  2. After rotation, remove the checkpoint refs that retain the file and expire unreachable git objects. Confirm the exact targets before deleting refs.
  3. Run a server-side scan against the actual GitHub remote and any CI artifact store. A local remote-tracking check cannot prove the remote never received the objects.
  4. Add a secret scanner to pre-commit and CI, and block environment-style files even on checkpoint or backup refs.

Medium

PAR-004: Redis locks have no ownership token

Race condition

Every execution lock uses the same value, 1. Refresh overwrites the key without comparing ownership, and release performs an unconditional delete. If worker A pauses long enough for its lock to expire, worker B can acquire the same lock. When A reaches finally, it can delete B's lock. Worker C can then acquire the key and run concurrently with B.

This recreates the duplicate review behavior the lock was intended to prevent: parallel LLM spend, competing checkpoints, duplicate comments, and inconsistent stage state. The short enqueue lock uses the same unconditional delete pattern after a 30-second TTL.

Required fix

  1. Create a cryptographically random owner token for each acquisition.
  2. Use atomic compare-and-expire for refresh and compare-and-delete for release, implemented with Redis Lua or an equivalent transaction.
  3. Add a monotonic fencing token checked by database writes if stale workers must be prevented from committing after lock loss.
  4. Test expiry, reacquisition, stale release, and watchdog cleanup races.

Medium

PAR-005: Webhook deliveries are not idempotent

Replay + retry

The delivery ID is recorded but never used as a deduplication key. An opened or reopened event performs visible GitHub side effects, inserts a new review, and queues work each time it is handled. There is no uniqueness constraint on the delivery ID and no atomic claim before side effects.

Normal GitHub retries after a timeout or partial failure can therefore duplicate comments and reviews. A captured signed request could also be replayed while the webhook secret remains valid.

Required fix

  1. Create a webhook-deliveries table with a unique delivery ID and event type.
  2. Atomically claim the delivery before any GitHub side effect or queue send.
  3. Persist completion and failure state so retries can safely resume instead of repeat.
  4. Make reaction and acknowledgment creation independently idempotent.

Medium

PAR-006: API input and costly actions are unbounded

Resource exhaustion

The dashboard proxies arbitrary JSON to the worker. The worker checks only that repo and body are truthy, then sends the body to embedding and classification providers and stores the result. There are no length, shape, depth, repository-format, content-type, or per-actor quota controls. The webhook also reads the complete body before applying any application-level size policy.

Combined with PAR-001 or PAR-002, this allows an inexpensive account or public comment to amplify model spend and database growth. Cloudflare and GitHub platform limits reduce maximum size but do not provide business-level abuse control.

Required fix

  1. Validate all inputs with one explicit schema and reject unknown fields.
  2. Set conservative byte and character limits before model calls and database writes.
  3. Rate-limit by user, repository, installation, and action type. Add daily cost budgets and 429 responses.
  4. Return 400 or 413 for client errors instead of reflecting provider or database failures as 500 responses.

Medium

PAR-007: Error redaction is fragmented and incomplete

Information disclosure

One sanitizer covers several credential formats, while stage failure persistence uses a separate two-pattern regular expression. Neither centralizes redaction for database URLs, cookies, generic API secrets, Redis credentials, or all provider key formats. The dashboard failure route returns stored error stacks, delivery IDs, error details, and the full timeline to the client.

Provider SDK and HTTP errors frequently include response bodies or request context. If a secret reaches an exception, the current path may persist it and expose it through the dashboard. PAR-001 makes this materially easier to exploit.

Required fix

  1. Use one redaction function for every log, database error field, queue error, and HTTP response.
  2. Store structured error codes and safe summaries. Keep raw stacks out of production responses.
  3. Add redaction coverage for credentials, cookies, connection URLs, private keys, signed URLs, and high-entropy assignments.
  4. Add canary-secret tests that exercise failure persistence and the dashboard response end to end.

Medium

PAR-008: LLM prompts mix instructions with untrusted repository content

Model integrity

File names, diffs, prior findings, stored rule bodies, and developer comments are directly interpolated into instruction-bearing prompts. A malicious change can include text that imitates prompt instructions or closes the Markdown fence. Stored rules are especially sensitive because they are reused across future reviews.

Prompt wording alone cannot create a reliable security boundary. The model's structured output is still trusted for finding bodies, file names, lines, and classifications before those outputs affect GitHub comments or rule state.

Required fix

  1. Separate system instructions from untrusted content using provider-native message roles and structured payloads.
  2. State explicitly that repository text is data, then enforce downstream allowlists regardless of model response.
  3. Validate file names against the actual diff, line numbers against changed hunks, severities against the enum, and rule IDs against the supplied set.
  4. Strip or neutralize bot-generated mentions and dangerous link schemes before posting to GitHub.

PAR-009: Wrangler 3 development chain has known advisories

Dev and CI only

The full npm advisory check reports six vulnerable package nodes through wrangler@3.114.17: Wrangler, esbuild, Miniflare, Sharp, Undici, and ws. The advisories include development-server cross-origin reads, HTTP desynchronization, decompression or fragmentation denial of service, and image-processing flaws.

The production-only scan reports zero advisories across 58 production dependencies. This finding therefore affects developer workstations and CI rather than the deployed Worker bundle. npm recommends upgrading to Wrangler 4.122.0, which is a major-version change and requires compatibility testing.

Required fix

  1. Upgrade Wrangler in a dedicated branch and run Worker build, tests, local Miniflare tests, and a preview deployment.
  2. Do not expose local development servers to untrusted networks before upgrading.
  3. Run both production-only and full dependency audits in CI, with separate policies for runtime and toolchain findings.

What went wrong

The vulnerabilities are connected. The system built good reliability controls around queue execution, but its authorization model stopped at the outermost signature or login check.

1. Identity was mistaken for authorityGitHub OAuth proves who signed in. GitHub webhook HMAC proves who sent the event. Neither proves permission to read a specific repository or change its policy.
2. State-changing decisions were delegated to free textA comment classifier can turn arbitrary prose into a persistent active rule. Explicit authorization is absent before this write.
3. Shared credentials flattened trust boundariesThe dashboard forwards one worker bearer secret, and both services use broad database access. Once a dashboard session passes, repository isolation no longer exists.
4. Reliability mechanisms lacked adversarial ownershipLocks, retries, error capture, and delivery IDs were designed for normal failure but not replay, stale-owner races, tenant isolation, or secret-bearing errors.
Core lesson: HMAC verification, OAuth login, queue locks, and structured LLM output are useful controls, but none of them authorize a user to act on a repository. Authorization must be explicit at every repository-scoped read and write boundary.

Controls already working

The codebase has useful security foundations. They should be preserved while the trust model is repaired.

Webhook authenticity

GitHub webhook bodies are verified with HMAC-SHA256 over the raw payload, followed by a constant-time comparison.

SQL injection resistance

Neon tagged-template queries bind user-controlled values instead of concatenating SQL strings.

Production dependency posture

The production-only npm advisory scan is clean at the time of audit.

Secret-file ignore rules

Current local environment files are ignored. The remaining problem is historical checkpoint reachability, not the current index.

Resumable queue design

SHA pinning, per-file checkpoints, subrequest budgets, and completion guards reduce accidental duplicate work.

Automated regression coverage

The test suite covers webhook verification, retries, queue behavior, provider failover, diff parsing, rule handling, and redaction helpers.

Scope and limitations

  • Audited the current working tree, including uncommitted user changes. Application files were not modified.
  • Reviewed the Worker, Next.js dashboard, database migrations, shared types, package graph, tests, documentation, and local git history.
  • Did not perform active exploitation against deployed Cloudflare, Vercel, GitHub, Neon, Upstash, or LLM-provider accounts.
  • Did not verify production environment variables, GitHub App permissions, Cloudflare firewall rules, Vercel access controls, database roles, backups, or remote git server object reachability.
  • The secret finding is based on high-confidence local pattern detection and configuration context. Credential validity was not tested.
  • Line numbers may move after the uncommitted working-tree changes are committed or edited.
